# 站内系列栏目 — 设计文档

日期：2026-08-26
状态：已评审（用户在对话中确认数据落在 series.json）
分支：`claude/topic-series-publishing-plan-meauda`

## 1. 背景与目标

站上现在只有分类和标签两种归拢方式，两者都是**无序集合**：进了「03质量控制」
的文章彼此平级，读者看不出「这几篇是一条线，该按这个顺序读」。

而知识库里大量内容天然成串 —— ELISA 的 MRD 建立、稀释线性、平行性验证是一条线；
结构表征从早研到 BLA 是另一条线。这些顺序信息目前完全丢失。

**目标**：让一组文章能以**指定顺序**成为一个「系列」，有自己的落地页与简介，
读者在任一篇里都能看到自己身处系列何处、上下篇是什么。

## 2. 为什么是呈现层，不是流水线

原始设想是「规定专题 → 从库里收集相关文档 → 制定发布计划 → 审核后按计划发布」，
即在流水线侧做系列化选题。放弃这条路的三个理由：

1. **校验器与「单篇引子」深度绑定。** 让模型规划多篇文章的大纲，意味着要为
   「大纲里每条论断」另建一套真实性核验。`verify.py` 是整条流水线的安全阀，
   为一个还没验证过价值的功能去改它，风险与收益不成比例。
2. **没有真实样本可参照。** 站上真正发布的只有 3 篇，`_review/` 还压着 9 篇待
   放行。没有一个跑通的系列，无从判断「AI 规划的系列大纲」好不好。
3. **呈现层能先把价值兑现。** 系列的读者价值（有序、有上下文、看得见全貌）
   全部落在呈现层。先手工攒出真系列观察效果，再决定要不要自动化选题。

**本次不做**：不碰 `pipeline/` 任何代码，不碰 posts 的 frontmatter schema，
不做系列 RSS，不做跨系列推荐。

## 3. 决策记录

| 决策项 | 结论 | 理由 |
|---|---|---|
| 系列归属与顺序存放位置 | `src/content/series.json` 单文件，顺序 = 数组顺序 | 用户决策。调整次序只改一个文件；写进 frontmatter 要改 N 个文件，且序号撞车没人拦 |
| 文章 frontmatter | **一个字段都不加** | 两条产出通道（`main.assemble_frontmatter`、`drafts.fill_defaults`）与 posts schema 全部不动，流水线零风险 |
| 未发布条目 | 显式写 `{"planned": "标题"}`，页面显示为「待发布」 | 这就是原始设想里的「发布计划」，5 行实现。更重要的是它让下一条成立 |
| 错拼的文章 id | **构建直接失败** | 手写 JSON 最容易踩的坑是 id 打错。若容许「找不到就当作待发布」，打错的 id 会静默变成一条幽灵条目 —— 与校验器同一个道理：拦不住就别上线 |
| 一篇文章属于多个系列 | **构建直接失败** | 文章页的系列归属提示只有一处，属于两个系列时显示哪个都是错的。与其静默取第一个，不如报错 |
| 数据加载方式 | Astro 原生 `file()` loader + zod schema | 已装的 astro 7.2.6 自带（`astro/loaders` 导出 `file`）。比手写 fs 读取少一层代码，且顺带拿到 shape 校验 |
| 系列页版式 | 目录式编号列表，不是文章卡片流 | 卡片流表达不出顺序，也放不下「待发布」这种无链接条目 |

## 4. 数据结构

`src/content/series.json`：

```json
[
  {
    "id": "单抗表征方法",
    "title": "单抗表征方法",
    "description": "一句话说明这个系列讲什么、按什么线索展开。",
    "entries": [
      { "post": "00基础-生物制品-单抗" },
      { "planned": "光散射技术表征生物药" }
    ]
  }
]
```

- `id`：URL 片段，站点路径为 `/series/<id>`。`file()` loader 要求每条有唯一 `id`
- `entries` 数组顺序**就是**系列阅读顺序，不另设序号字段 —— 序号字段会与数组
  顺序产生两个真相
- 每个 entry 恰好有 `post` 或 `planned` 之一，两者都有或都无一律构建失败

## 5. 序号与上下篇的语义

- **「第 N 篇 / 共 M 篇」中的 N 与 M 都按完整 entries 计**，含待发布条目。
  这样 M 表达的是「这个系列计划写多少篇」，与「发布计划」的定位一致
- **上一篇 / 下一篇跳过待发布条目**：待发布的没有页面可链
- 一个系列若一篇都还没发布，它仍出现在 `/series` 索引页上（那正是一份计划），
  但没有任何文章页会显示它

## 6. 组件划分

| 文件 | 职责 |
|---|---|
| `src/content/series.json` | 数据。唯一的真相来源 |
| `src/content.config.ts` | 声明 series collection 与 zod schema（shape 校验） |
| `src/lib/series.ts` | 唯一一处解析逻辑：把 entries 解析成文章对象，做两项硬校验，算上下篇 |
| `src/pages/series/index.astro` | 系列索引 |
| `src/pages/series/[series].astro` | 单个系列的目录页 |
| `src/layouts/Post.astro` | 顶部系列归属提示 + 底部上下篇导航 |
| `src/pages/posts/[...slug].astro` | 把系列上下文算好传给 Post.astro |
| `src/components/Header.astro` | 主导航加「系列」 |

解析逻辑集中在 `src/lib/series.ts` 一处，三个页面都调它 —— 三处各写一遍必然漂移，
而漂移的后果是同一篇文章在系列页和文章页显示出不同的序号。
