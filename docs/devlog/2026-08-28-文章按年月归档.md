# 2026-08-28　文章目录按年月归档：posts/ 从平铺目录改成 YYYY-MM 子文件夹

## 背景

`src/content/posts/` 一直是平铺目录，2026-08-28 这天已经堆了 17 篇文章，而且
这个数字只会随流水线持续产出继续涨。校验没过的文章（`draft: true`）跟正式
文章同住一处——这是仓库既有设计，`README.md` 里写明白了：放行只是删掉
frontmatter 里 `draft: true` 那一行，不挪文件。人工想知道"哪几篇还压着草稿
等放行"，就得把 17 个（以后会更多）文件名逐个点开看 frontmatter，大海捞针。

目标：按年月（`YYYY-MM`）把文章分进子文件夹，翻找草稿时只用扫一个月的量。
**不改变"草稿与正式文章同住一处"这个既有设计**，只是把"一处"从一个平铺
目录变成按月分的多个子目录。

设计阶段跟用户确认了三项落地方式，并被用户纠正了一处（月份取值来源）：

| 决策项 | 结论 |
|---|---|
| 月份文件夹命名 | `YYYY-MM`（跟 `published_at`、devlog 文件名的日期风格一致，纯 ASCII） |
| 文章文件名（slug） | 保持不变，只挪目录，不加日期前缀（slug 同时是 URL、`published.json` 的 key、`series.json` 的引用，三处共享一个字符串，不能轻改） |
| "最新在顶部" | 不额外建索引——标准工具（GitHub 网页版/VS Code/`ls`/git）浏览目录都是字母序，没有命名手法能让它们自动倒序，做索引的维护成本跟"减少翻找草稿"这个诉求不成比例 |
| 月份取值来源 | 不读 frontmatter 的 `date` 字段，四个写入点各自用"运行当天"直接算（原因见「实现」一节） |

## 变更

- 新增：`pipeline/main.py` 的 `_all_posts()` / `post_path()` 两个共享助手，
  给 `reconcile()`、`related_published()`、`repair.py` 的扫描和四个写入点
  统一用，避免五处各自实现一份、之后行为漂移
- 修改：`reconcile()`、`repair.py` 的扫描逻辑，从平铺 `glob('*.md')` 改成
  递归 `_all_posts()`（不改的话分月后 `reconcile()` 会把 `published.json`
  现有记录全部当"文件没了"销掉——重演过一次的事故）
- 修改：四个写入点（`main.run_auto()`、`seed.process()`、
  `drafts.run_drafts()`、`routinerun.run()`），产出文件落在
  `posts/<运行当天算出的 YYYY-MM>/<slug>.md`
- 修改：`seed.py` 的 `related_published()`，改用 `_all_posts()` 查已发布
  文章标题，不再假设平铺（原来拼平铺路径找不到就静默退化成显示 slug）
- 修改：`seed.process()`，重跑已发布文章时如果算出的月份变了，删除旧月份

- 修改：`drafts.run_drafts()`、`routinerun.run()`，slug 冲突/跳过检测覆盖

- 新增依赖：`github-slugger`（`package.json` / `package-lock.json`）
- 修改：`src/content.config.ts`，`glob()` loader 加 `generateId`，保证
  `entry.id` 不受目录嵌套影响
- 迁移：17 篇现有文章 `git mv` 进 `src/content/posts/2026-08/`（纯 rename，
  文件内容零改动，git 历史保留）
- 修改：`README.md` 四处明确依赖平铺结构的描述，同步成按年月归档
- 新增：`pipeline/test_pipeline.py` 8 个自检（详见「验证」），更新 7 处
  既有断言的落点计算

## 实现

### 月份不读 frontmatter 的 `date` 字段，四个写入点各自用"运行当天"算

最初设计想直接用 `date` 字段算月份，用户在评审时指出问题：`drafts.py`
的人工投稿通道，`date` 允许回溯。`fill_defaults()`（`pipeline/drafts.py:58`）：

```python
'date': fm.get('date') or _git_first_commit_date(path) or dt.date.today().isoformat(),
```

优先取稿子里手写的旧日期，其次取 `drafts/` 目录里稿子首次提交的 git 日期，
两者都可能早于稿子真正被流水线处理、落进 `posts/` 的那一天。若归档月份
跟着 `date` 走，"今天刚落地的稿子"可能被塞进几个月前的文件夹，翻找"最近
发生了什么"反而更难——直接违背这次改动的目的。

改成月份直接取 `dt.date.today().strftime('%Y-%m')` 后，`date` 字段继续只管
文章自己显示的日期（站点排序、frontmatter），跟归档目录彻底脱钩。这条理由
写进了 `post_path()` 的文档字符串（`pipeline/main.py:193-200`），不只是
留在设计文档里。三条自动化通道（`run_auto`/`seed.process`/`routinerun.run`）
其实不受影响——它们的 `date` 本来就是当天现算的，跟"运行当天"永远同一天；
只有 `drafts.py` 这条通道两者可能不同，也正是这条通道最需要这条规则。

四个写入点：`pipeline/main.py:269`（`run_auto`）、`pipeline/seed.py:189`
（`process`）、`pipeline/drafts.py:74`（`run_drafts`）、
`pipeline/routinerun.py:89`（`run`，这里写的是 `date[:7]` 而不是重新
`strftime`，因为 `routinerun.run()` 本来就有 `today` 参数可覆盖，直接切
已经算好的 `date` 字符串省一次日期对象构造）。

### `seed.process()` 重跑清孤本

`process()` 是唯一会对已存在 slug 整篇覆盖重写的通道——人工改完源笔记后
重跑同一篇引子；`run_auto` 靠 `pick_next` 天然不会选中已发布的，
`drafts`/`routinerun` 遇到重名直接报错跳过，不覆盖。`pipeline/seed.py:189-193`：

```python
month = dt.date.today().strftime('%Y-%m')
out = mn.post_path(posts_dir, g.slug, month)
old = mn._all_posts(posts_dir).get(g.slug)
if old and old != out:
    old.unlink()   # 同一 slug 换月份重发（人工改完笔记重跑），旧文件删掉避免留孤本
```

如果这次重跑算出的月份跟旧文件所在月份不同（比如月初手改了篇上个月发的
文章的源笔记），写入前用 `_all_posts()` 查到旧路径并删除，保证一个 slug
任何时刻只有一份活文件，不会同时躺在两个月份文件夹里。评审留了一条已知
取舍没有处理：先 `unlink()` 旧文件再写新文件，中间进程被杀掉理论上两份
都丢——单线程流水线里这个窗口极窄，按计划原样保留，没有另外加原子写保护，
收益不值当。

### `generateId` 必须复刻 `github-slugger`，不能只取文件名

`src/pages/posts/[...slug].astro` 直接拿 `entry.id` 当 URL，
`src/lib/series.ts` 拿 `entry.id` 匹配 `series.json`；Astro 的 `glob()`
loader 默认会把子目录路径也编进 `id`，分文件夹后不处理的话两处都会失效
（后者是 `loadSeries()` 里故意设计的硬校验，会让构建直接失败，不会静默
上线，但同样要避免）。

第一版直觉是"`generateId` 只取文件名最后一段"就够了，但设计阶段用
`node -e "require('github-slugger').slug(...)"` 实测了当时全部 17 篇文章
的文件名：16 篇结果跟文件名原样一致，唯一例外是
**`HCP鉴定与定量` → `hcp鉴定与定量`**（大写字母被转小写）——因为 Astro
非 legacy 模式的默认 `generateId`，对没有目录前缀的单段路径本来就会先过
一遍 `githubSlug()` 再当 id，不是原样使用文件名。如果自定义 `generateId`
只是简单地 `entry.split('/').pop()`，站点原有的 `hcp鉴定与定量` 这个 URL
会因为这次迁移悄悄变成 `HCP鉴定与定量`（大小写不一致于迁移前），是一处
会被忽略的静默改动。最终实现（`src/content.config.ts:21`）：

```ts
generateId: ({ entry }) => githubSlug(entry.split('/').pop().replace(/\.md$/, '')),
```

`npm run build` 后本次会话实测 `find dist -type d -iname "*hcp*"`：
`dist/posts/hcp定量-ibaq`（文件名本来就是小写，不受影响）和
`dist/posts/hcp鉴定与定量`（确认被转成小写，这正是要验证的行为）都生成了，
说明这一步复刻确实生效。

### 一处真实的测试判别力问题（Task 3 评审抓到）

计划里 `test_related_published_finds_articles_across_month_folders` 第一版
只断言 `rs[0]['related'] == ['old-one']`——但 `related_published()` 返回
`[(slug, title)]`，`process()` 组装返回值时只取
`[s for s, _ in rel]`，标题在这一步就被丢了。这意味着无论跨月份的标题
查找是查到了还是没查到，这条断言看到的都是同一个 `'old-one'`，测不出新
代码到底有没有起作用——评审记录显示这条测试在生产代码改之前就已经
PASS，跟"RED 阶段该失败"的预期直接矛盾，说明是计划里这条测试本身写错了。

修法：把断言换成读渲染出来的文章正文（`pipeline/test_pipeline.py:1403-1411`）——
查到标题会渲染成 `[旧文](/posts/old-one)`，查不到会退化成
`[old-one](/posts/old-one)`（链接文字变成 slug 本身），这是标题查找有没有
跨月份生效唯一能从外部观察到的地方：

```python
assert '[旧文](/posts/old-one)' in text, text
```

记一笔供以后写测试时留意：断言要测的字段如果在被测函数返回之前就已经被
丢弃了，断言本身就失去了判别力；写完新测试要先跑一遍确认它真的会因为
旧代码而 FAIL（RED），不能想当然。

## 实测修正

最终评审（全分支通读）抓到一个真实 bug：`pipeline/main.py` 的
`run_auto()` 拿到了月份落点（Task 2），却没有 `seed.process()`
（Task 3）那段"换月份重发时删旧文件"的清理逻辑。

**问题是怎么漏的**：本篇「实现」一节「`seed.process()` 重跑清孤本」
原来写着"`run_auto` 靠 `pick_next` 天然不会选中已发布的"——这句判断
是错的。`select_.py:130-131` 的 `pick_next()`：

```python
rec = by_tag.get(g.tag)
if rec is None or (rec.get('source_hash')
                   and rec['source_hash'] != g.source_hash):
    return g
```

只要账本里记录的 `source_hash` 跟这一轮算出来的组哈希对不上，就会
重新选中这个已发布的组——这正是 `test_backfilled_record_is_not_
republished` 已经在测的行为（"有哈希且对不上才重发"），不是新发现的
特性，是设计阶段没把这条已有行为跟"`run_auto` 会不会撞见已发布 slug
换月份"这件事联系起来。源笔记内容一变，下次 `run_auto` 就会重新生成
对应文章；如果这次生成落在新的月份文件夹，旧月份那份不会被清掉——
同一个 slug 在两个月份目录各留一份，`_all_posts()` 按 slug 做 key 的
字典构建会把其中一份覆盖掉，只剩一条可查的路径，`reconcile()`/
`repair.py` 看不到另一份，"删文件 = 退稿"的约定对那一份也就失效了。

**改了什么**：

- `pipeline/main.py`：`run_auto()` 在 `post_path()` 算出新落点后，比照
  `seed.process()` 的写法，用 `_all_posts()` 查旧路径，跟新落点不同就
  先删旧文件再写新文件
- `pipeline/drafts.py`、`pipeline/routinerun.py`：循环内重扫
  `_all_posts()` 那两处各补一句注释，讲清楚"为什么不缓存在循环外"
  （防同一批产出里出现重复 slug 时判重漏判），没有行为改动
- `pipeline/routinerun.py`：`month = date[:7]` 补注释，写明这行现在
  是对的，是因为这条通道的 `date` 恒等于运行当天——哪天这条通道也
  允许 `date` 回溯，这里要跟着改回单独计算月份
- `docs/superpowers/specs/2026-08-28-文章按年月归档-design.md` 3.1
  节：改掉"`run_auto` 靠 `pick_next` 天然不会选中已发布的"这句错误
  判断，说明 `run_auto` 也需要跟 `process()` 一样的清理
- 本篇「动了哪些文件」一节的脚注：`9c1d779` 被误称为"master 合并
  基线"，改成准确描述（见上方脚注正文）
- `pipeline/test_pipeline.py`：新增
  `test_run_auto_moves_article_to_new_month_removes_old_copy`，构造
  "账本里的 `source_hash` 跟当前不一致 + 旧文件躺在别的月份文件夹"
  这个场景。按 TDD 走了一遍：改 `main.py` 之前单独跑这个新测试，
  `AssertionError: 旧月份文件夹的孤本应该被清掉`，确认会因为旧代码
  失败（RED）；改完之后单独跑 PASS（GREEN），再跑全量自检确认没有
  连带影响
