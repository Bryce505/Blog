# 2026-08-27　定时发布连续第三晚未触发，cron 挪出整点 + 加一条备份触发

## 背景

用户反馈：北京时间 21:00（`publish.yml` 定时点）已过、22 点也过了，博客站上
没有新文章，怀疑定时发布的 bug 还在。查 Actions 记录，实测确认这不是猜测：

**`publish` workflow 全部触发记录里，`schedule` 事件只有两次成功触发过，
且一次比一次晚，第三次（今晚）截至排查时彻底没出现：**

| 日期 | 预定时间 (UTC) | 实际触发 (UTC) | 延迟 | 备注 |
|---|---|---|---|---|
| 08-25 | 13:00 | 13:41:36 | 41 分钟 | [run 32854869640](https://github.com/Bryce505/Blog/actions/runs/32854869640) |
| 08-26 | 13:00 | 13:46:21 | 46 分钟 | [run 32976194195](https://github.com/Bryce505/Blog/actions/runs/32976194195) |
| 08-27（今晚）| 13:00 | **无** | **≥ 90 分钟仍未出现** | 查到 UTC 14:30（北京 22:30）为止，`list_workflow_runs` 里这一天一条 `schedule` 记录都没有——不是排队中（`status` 会显示 `queued`），是 GitHub 的调度器压根还没派发这次运行 |

同一时间窗口里的对照组：`workflow_dispatch` 触发的运行（08-26 那两次，
23:23、23:36 UTC）都是秒开、立即 `in_progress`——延迟只发生在 `schedule`
事件上，`workflow_dispatch`/`push` 不受影响，说明不是仓库或账号权限问题，
是 GitHub 对 `schedule` 事件本身的调度策略。

排查工作流本身排除了代码层面的可能：
- `state: active`，workflow 没被禁用
- 当前分支的 `publish.yml` 与 `origin/master` 逐字节相同（`git diff` 空）
- cron 表达式 `0 13 * * *` 本身语法有效——过去两天确实触发过，只是晚

昨天（`docs/devlog/2026-08-26-定时发布排查.md`）已经查到过这个现象，结论是
「GitHub 调度延迟，非代码问题」，没有动 workflow 配置。今晚是这个现象
**连续第三次复现，且延迟幅度还在变大**（41 → 46 → ≥90 分钟且尚未出现），
不是偶发；GitHub 官方文档对 `schedule` 事件的说明原话是：

> High load times include the start of every hour. To decrease the chance
> of delay, schedule your workflow to run at a different time of the hour.

`0 13 * * *` 恰好卡在文档点名的「全平台最挤」的那一分钟——分钟字段填 `0`，
等于自己选了最容易被拖延的时间点。这是可以从仓库这边改掉的部分：换一个
非整点的分钟，不能保证零延迟（GitHub 没有给过延迟上限的承诺，也没有
「一定会触发」的 SLA），但去掉了「自己选了最差时段」这一个可控因素。

## 变更

- 修改：`publish.yml` 的 `schedule` cron 由 `0 13 * * *`（UTC 整点）改为
  `13 13 * * *`（UTC 13:13 = 北京 21:13）
- 新增：`publish.yml` 补一条备份 cron `37 15 * * *`（UTC 15:37 = 北京
  23:37），与主触发相隔两个多小时
- 修改：`README.md` 工作流一览表里 `publish.yml` 的触发方式说明，同步成
  两条定时时间

## 实现

**只挪分钟，不改小时，不改「一天一次」的产品预期。** 目标时间本来就是
「北京时间 21 点左右」，挪 13 分钟不影响这个预期，只是不再刻意撞在
GitHub 自己文档点名的高峰分钟上。

**加一条备份触发，而不是重写调度逻辑去做「已发布就跳过」的判断。**
考虑过给两条 cron 加一层「今天 UTC 日期 `published.json` 里已经有记录就
跳过第二条」的判断，需要拆成 `check` + `publish` 两个 job 或者给发文三步
分别加 `if:` 条件，改动面明显更大、给这条工作了三天都没出过大问题的
workflow 引入新的分支逻辑，出错的地方也更多。评估后放弃：

- 两条 cron 都落在既有的 `concurrency: group: publish`
  （`cancel-in-progress: false`）里，天然串行，不会同时写
  `published.json` 打架——这层保护本来就有，不用新加
- 备份触发如果在主触发已经成功之后才跑，后果只是「同一天多发一篇」而
  不是「发错」或「发重复」——`used_seeds`/`published.json` 去重已经保证
  不会选中同一篇笔记，`_review/` 时代那种「重复失败」的 bug（见
  `2026-08-26-定时发布排查.md`）在草稿位放行改造后已经不存在（`seed.run()`
  的 `used_seeds` 来自 `published.json` 全量记录，草稿也算数）
- 查了 `published.json` 实际记录：08-26 那天已经出过 7 篇（含手动触发），
  「一天不止发一篇」本来就是这条流水线的常态，不是要严格保证的不变量。
  加一条可能偶尔重复触发的备份，产品语义上没有引入新问题

**两条 cron 间隔两个多小时（13:13 → 15:37），不是紧挨着重试。** 如果
GitHub 那一刻整个平台都在过载，几分钟后再试大概率还是撞上同一波高峰；
隔开几个小时才是真的在降低「两条都被拖延」的相关性。

**没有去做的事：验证「今晚这次到底是极端延迟还是被跳过」。** 这需要
等更久（GitHub 没给延迟上限，可能几小时后才出现，也可能真的不出现了）,
不是这次排查能在一次会话里等到确定结果的事。这条改动是在「不能 100% 确定
根因是延迟还是丢失」的前提下做的防御性修复——两种情况这条改动都对症：
延迟靠挪开整点缓解，丢失靠备份触发兜底。

## 验证

- **YAML 语法**：`python3 -c "import yaml; yaml.safe_load(open('.github/workflows/publish.yml'))"`
  解析通过，两条 cron 均正确解析为 `13 13 * * *` 与 `37 15 * * *`
- **`python pipeline/test_pipeline.py`：137/137 全绿**（这次改动没碰
  `pipeline/` 任何一个 `.py` 文件，纯 workflow 配置 + 文档，自检数字不变
  只是确认没有连带弄坏什么）
- **`npm run build`：27 个页面构建成功**，7 篇正式文章（其余 7 篇是
  `draft: true` 待人工过目的存量草稿，这是另一套「草稿位放行」机制，
  跟这次排查的调度延迟是两回事，没有混着改）
- **调度延迟本身无法在这次会话里当场复现验证**：这类问题的性质决定了
  「测试」只能是接下来几天观察 Actions 里 `schedule` 事件的真实触发时间
  是不是比整点方案更接近预定点、以及备份触发有没有被用上。这条改动合并
  到 `master` 之后才会影响真实的定时任务（GitHub 只认默认分支上的 cron
  配置），本分支这次的验证止于「配置正确、没有连带破坏」，端到端的
  「调度是否真的更准时」需要仓库所有者合并后在接下来几晚上观察确认。

## 实测修正

改动合并到 `master`（commit `124cc02`）后，当场用 `workflow_dispatch`
（seed 模式、`--publish`）在 `master` 上手动跑了一次
（[run 33083563034](https://github.com/Bryce505/Blog/actions/runs/33083563034)），
目的有两个：验证合并后的 workflow 全链路（凭据、pipeline、校验、
commit + push）没有被这次改动带坏；顺带解决用户当晚反馈的直接症状——
今晚的文章还没出来。

**结果**：UTC 14:40:43 触发，14:46:39 完成，耗时 5 分 56 秒。选中引子
`乌司他丁(Ulinastatin)文献综述-BJ044项目.md`，减法模式，28,196 → 22,586
字符，校验全过（`logs/verify-2026-08.md` 记了「通过」），直接发布、
没有落草稿位。产出提交 `bc3db96 自动发布：2026-08-27`：`published.json`
新增一条无 `draft` 字段的记录，`npm run build` 后确认
`dist/posts/乌司他丁-ulinastatin-文献综述-bj044项目/index.html`
实际生成，站点正式文章数 7 → 8。今晚「过了 21 点没有新文章」这个直接
症状，到这一步已经用真实产出解决。

**这次手动验证覆盖不到的部分**：`workflow_dispatch` 走的不是
`schedule` 事件，测的是「合并后的 workflow 本身没坏」，不是「cron
挪出整点之后，`schedule` 事件是不是真的更准时触发了」——这仍然要等
明天 UTC 13:13（主触发）或今晚 UTC 15:37（备份触发，仅剩这一次机会，
过了今天就要等明天主触发）的真实 `schedule` 记录才能确认，本分支的
「实测」到这里为止；`schedule` 触发时间的后续观察记在这篇日志之外，
或由仓库所有者在接下来几天自行核对 Actions 记录。
