# 2026-08-27　定时发布连续第三晚未触发，cron 挪出整点 + 加一条备份触发

## 背景

用户反馈：北京时间 21:00（`publish.yml` 定时点）已过、22 点也过了，博客站上
没有新文章，怀疑定时发布的 bug 还在。查 Actions 记录，实测确认这不是猜测：

**`publish` workflow 全部触发记录里，`schedule` 事件只有两次成功触发过，
且一次比一次晚，第三次（今晚）截至排查时彻底没出现：**

| 日期 | 预定时间 (UTC) | 实际触发 (UTC) | 延迟 | 备注 |
|---|---|---|---|---|
| 08-25 | 13:00 | 13:41:36 | 41 分钟 | [run 32854869640](https://github.com/Bryce505/Blog/actions/runs/32854869640) |
| 08-26 | 13:00 | 13:46:21 | 46 分钟 | [run 32976194195](https://github.com/Bryce505/Blog/actions/runs/32976194195) |
| 08-27（今晚）| 13:00 | **无** | **≥ 90 分钟仍未出现** | 查到 UTC 14:30（北京 22:30）为止，`list_workflow_runs` 里这一天一条 `schedule` 记录都没有——不是排队中（`status` 会显示 `queued`），是 GitHub 的调度器压根还没派发这次运行 |

同一时间窗口里的对照组：`workflow_dispatch` 触发的运行（08-26 那两次，
23:23、23:36 UTC）都是秒开、立即 `in_progress`——延迟只发生在 `schedule`
事件上，`workflow_dispatch`/`push` 不受影响，说明不是仓库或账号权限问题，
是 GitHub 对 `schedule` 事件本身的调度策略。

排查工作流本身排除了代码层面的可能：
- `state: active`，workflow 没被禁用
- 当前分支的 `publish.yml` 与 `origin/master` 逐字节相同（`git diff` 空）
- cron 表达式 `0 13 * * *` 本身语法有效——过去两天确实触发过，只是晚

昨天（`docs/devlog/2026-08-26-定时发布排查.md`）已经查到过这个现象，结论是
「GitHub 调度延迟，非代码问题」，没有动 workflow 配置。今晚是这个现象
**连续第三次复现，且延迟幅度还在变大**（41 → 46 → ≥90 分钟且尚未出现），
不是偶发；GitHub 官方文档对 `schedule` 事件的说明原话是：

> High load times include the start of every hour. To decrease the chance
> of delay, schedule your workflow to run at a different time of the hour.

`0 13 * * *` 恰好卡在文档点名的「全平台最挤」的那一分钟——分钟字段填 `0`，
等于自己选了最容易被拖延的时间点。这是可以从仓库这边改掉的部分：换一个
非整点的分钟，不能保证零延迟（GitHub 没有给过延迟上限的承诺，也没有
「一定会触发」的 SLA），但去掉了「自己选了最差时段」这一个可控因素。

## 变更

- 修改：`publish.yml` 的 `schedule` cron 由 `0 13 * * *`（UTC 整点）改为
  `13 13 * * *`（UTC 13:13 = 北京 21:13）
- 新增：`publish.yml` 补一条备份 cron `37 15 * * *`（UTC 15:37 = 北京
  23:37），与主触发相隔两个多小时
- 修改：`README.md` 工作流一览表里 `publish.yml` 的触发方式说明，同步成
  两条定时时间

## 实现

**只挪分钟，不改小时，不改「一天一次」的产品预期。** 目标时间本来就是
「北京时间 21 点左右」，挪 13 分钟不影响这个预期，只是不再刻意撞在
GitHub 自己文档点名的高峰分钟上。

**加一条备份触发，而不是重写调度逻辑去做「已发布就跳过」的判断。**
考虑过给两条 cron 加一层「今天 UTC 日期 `published.json` 里已经有记录就
跳过第二条」的判断，需要拆成 `check` + `publish` 两个 job 或者给发文三步
分别加 `if:` 条件，改动面明显更大、给这条工作了三天都没出过大问题的
workflow 引入新的分支逻辑，出错的地方也更多。评估后放弃：

- 两条 cron 都落在既有的 `concurrency: group: publish`
  （`cancel-in-progress: false`）里，天然串行，不会同时写
  `published.json` 打架——这层保护本来就有，不用新加
- 备份触发如果在主触发已经成功之后才跑，后果只是「同一天多发一篇」而
  不是「发错」或「发重复」——`used_seeds`/`published.json` 去重已经保证
  不会选中同一篇笔记，`_review/` 时代那种「重复失败」的 bug（见
  `2026-08-26-定时发布排查.md`）在草稿位放行改造后已经不存在（`seed.run()`
  的 `used_seeds` 来自 `published.json` 全量记录，草稿也算数）
- 查了 `published.json` 实际记录：08-26 那天已经出过 7 篇（含手动触发），
  「一天不止发一篇」本来就是这条流水线的常态，不是要严格保证的不变量。
  加一条可能偶尔重复触发的备份，产品语义上没有引入新问题

**两条 cron 间隔两个多小时（13:13 → 15:37），不是紧挨着重试。** 如果
GitHub 那一刻整个平台都在过载，几分钟后再试大概率还是撞上同一波高峰；
隔开几个小时才是真的在降低「两条都被拖延」的相关性。

**没有去做的事：验证「今晚这次到底是极端延迟还是被跳过」。** 这需要
等更久（GitHub 没给延迟上限，可能几小时后才出现，也可能真的不出现了）,
不是这次排查能在一次会话里等到确定结果的事。这条改动是在「不能 100% 确定
根因是延迟还是丢失」的前提下做的防御性修复——两种情况这条改动都对症：
延迟靠挪开整点缓解，丢失靠备份触发兜底。

## 实测修正

改动合并到 `master`（commit `124cc02`）后，当场用 `workflow_dispatch`
（seed 模式、`--publish`）在 `master` 上手动跑了一次
（[run 33083563034](https://github.com/Bryce505/Blog/actions/runs/33083563034)），
目的有两个：验证合并后的 workflow 全链路（凭据、pipeline、校验、
commit + push）没有被这次改动带坏；顺带解决用户当晚反馈的直接症状——
今晚的文章还没出来。

**结果**：UTC 14:40:43 触发，14:46:39 完成，耗时 5 分 56 秒。选中引子
`乌司他丁(Ulinastatin)文献综述-BJ044项目.md`，减法模式，28,196 → 22,586
字符，校验全过（`logs/verify-2026-08.md` 记了「通过」），直接发布、
没有落草稿位。产出提交 `bc3db96 自动发布：2026-08-27`：`published.json`
新增一条无 `draft` 字段的记录，`npm run build` 后确认
`dist/posts/乌司他丁-ulinastatin-文献综述-bj044项目/index.html`
实际生成，站点正式文章数 7 → 8。今晚「过了 21 点没有新文章」这个直接
症状，到这一步已经用真实产出解决。

**这次手动验证覆盖不到的部分**：`workflow_dispatch` 走的不是
`schedule` 事件，测的是「合并后的 workflow 本身没坏」，不是「cron
挪出整点之后，`schedule` 事件是不是真的更准时触发了」——这要等真实的
`schedule` 记录才能确认。

### 今晚 23:37（UTC 15:37）备份触发的实测结果：整 60 分钟没出现

改动合并（约 UTC 14:39）到备份触发点（UTC 15:37）之间隔了将近一小时，
是一次公平的测试窗口——不像今天的主触发点（UTC 13:13）改完就已经过去，
今天没有机会验证。从 UTC 15:37 起每隔约 9 分钟查一次
`list_workflow_runs`（`event: schedule`），到 **UTC 16:37（整 60
分钟）为止，`schedule` 记录仍然只有 08-25、08-26 那两条旧的，今晚这次
一次都没出现**——比这条改动之前唯二两次成功触发的延迟（41、46 分钟）
还要久，已经超出「只是比平时慢一点」能解释的范围。

**这对「延迟 vs 被跳过」意味着什么**：不能证明挪开整点这个改动是错的，
但也没能证明它管用——今晚这一次样本本身就没有落在「延迟后触发」这一边，
跟被跳过的表现没有区别。一个没有排除、但也没法在这次会话里验证的解释：
workflow 文件改动到备份触发点只隔了不到一小时，`schedule` 的调度可能
需要一点时间才会拿到默认分支上最新的 cron 配置——如果是这样，明天
UTC 13:13 那次主触发（离改动落地有近 23 小时的提前量）会是更公平的
测试，今晚这次备份触发反而是「改完立刻要用」的极端情况，不代表以后
每天都这样。这只是一个尚未证实的猜测，不是结论。

**没有再等更久或者再手动触发一次的原因**：今晚的直接症状（用户反馈的
"过了 21 点没有文章"）已经用上面那次 `workflow_dispatch` 解决了，
真有文章发出来了；`schedule` 触发是否可靠这件事本身没法靠在这次会话里
死等验证出来——GitHub 没有给过延迟上限也没有给过"一定触发"的承诺，
再等更久或者再手动跑一次都不会让这件事变得更确定。真正有效的验证只能是
明天 UTC 13:13 主触发的真实记录，已经设了自动检查，到时候的结果会
继续记在这篇日志里（或者由仓库所有者直接查 Actions 记录确认）。

### 临时诊断点（UTC 17:23）的实测结果：又一个整 60 分钟没出现

前一节结尾提出一个没证实的猜测："15:37 那次没触发，可能是文件刚改完、
调度还没拿到最新配置"——如果这个猜测成立，隔得更久之后再试的时段应该
更容易触发。为了不等到明天才多攒一个样本，临时在 `publish.yml` 里加了
第三条 cron `23 17 * * *`（UTC 17:23，离改动落地约 2.5 小时，比 15:37
那次多了一倍半的"生效时间"），commit `72c8c3b`，合并 `97583f1`，注释
里写明"用完即删"。

同样每隔约 9 分钟查一次（这次因为容器在等待期间重启了两次、Bash 后台
任务被冲掉重开了几轮），到 **UTC 18:21（离 17:23 过去 58 分钟，等同
整 60 分钟窗口）为止，`schedule` 记录依然只有 08-25、08-26 那两条旧的，
这次诊断触发也没有出现**。诊断任务完成后按计划移除，不留作常设第三条
触发（见上面 `publish.yml` 的改动）。

**这推翻了"调度还没生效"这个猜测**：15:37 和 17:23 之间隔了近两小时，
如果单纯是"配置还没被调度器拿到"，17:23 这次没道理还是同样的结果。
更值得注意的是：**今天从头到尾三个 `schedule` 时段——改动前的整点
13:00（一整天没触发）、改动后的 15:37（60 分钟没触发）、改动后的
17:23（60 分钟没触发）——没有一个成功触发过**。这不再像是"整点更容易
延迟"能单独解释的现象，更像是今天这个仓库（或者这个时间段的 GitHub
Actions）的 `schedule` 事件本身出了比"选错分钟"更大的问题——具体是
账号级别的调度积压、还是平台性的临时问题，这次会话里没有能力从外部
核实（`githubstatus.com`、`docs.github.com` 都被这个环境的出网代理
挡了，试过 `WebFetch` 和裸 `curl` 都是 403）。

**如实给这条改动一个当前状态判断，不往乐观了说**：cron 挪出整点本身
仍然是有官方文档依据、方向正确、不会带来副作用的改动，继续留着；但
截至这次会话结束，它*没有被证实解决问题*——三个时段全部落空，样本
质量比"证明有效"更接近"证明当天调度大范围失灵"。真正决定这条改动
最终有没有用的，是明天 UTC 13:13 那次主触发：那时候距离改动落地已经
过了近 23 小时，如果 GitHub 那边今天的问题只是临时性的，明天应该能看到
不一样的结果；如果明天这次同样长时间不触发，说明问题的根子不在"选错
分钟"，需要认真评估绕开 GitHub 自己 `schedule` 队列的方案——用外部
定时服务（如 cron-job.org、云函数的定时触发器）在固定时刻调用
`workflow_dispatch`，这条通道今天测了三次、每次都是秒开，是目前唯一
被反复验证可靠的触发方式。这个方案需要仓库所有者决定用什么外部服务、
把哪个权限范围的 token 交给它，这次会话没有自作主张去搭，留到明天有
决定性证据之后再谈。

### 尝试用 Claude Code 自己的 Routine 系统绕开 GitHub schedule 队列：没有成功

上一节提到的外部触发方案，第一反应是"不一定要接外部服务"——这次会话
本身就在用 Claude Code Remote 的 Routine（`send_later`/`create_trigger`）
按时唤醒自己，而且这条通道今天已经证明可靠（每条 `send_later` 提醒都
准时送达，包括容器重启之后）。于是尝试了一个更省事的方案：建一条绑定
在**当前会话**上的 Routine，每天定点直接调用
`mcp__github__actions_run_trigger` 触发 `workflow_dispatch`，完全不
经过 GitHub 自己的 `schedule` 队列。

`create_trigger` 建好后返回一条警告：`this trigger stores no MCP
connectors, so the sessions it fires will run without connector
(mcp__<server>__* ) tools`。当时的判断是"绑定的是本会话本身，应该沿用
本会话已经在用的 GitHub 工具，警告更可能是针对『新开会话』或『跨会话』
的场景"——没有把握，所以没有直接采信，而是用 `fire_trigger` 立即实测
了一次而不是空等到明天。

**实测结果：警告是真的。** `fire_trigger` 调用后等了约 5 分钟（用
`list_workflow_runs` 直接查，不等触发后的会话轮次自己送回来），GitHub
上没有出现任何新的 `workflow_dispatch` 记录——触发后的那次会话轮次，
不管是没拿到 `mcp__github__` 工具、还是调用失败，总之没有产生可观察
的效果。这条 Routine 因此**没有**实现设计目标：它不能在 GitHub
`schedule` 之外提供一条独立可靠的触发路径。

已用 `update_trigger` 把它禁用（`enabled: false`，没有删除，保留
配置和触发历史，`trig_018gTq1rPbjY5EfjAfbjAkWF`）——留着能跑但跑了没用
的东西，等于制造一个「看起来有备份、其实没有」的假象，比不设这条 Routine
更危险。

**这条路走不通不代表外部触发方案本身不可行**，只说明"用 Claude Code
自己的 Routine 系统调用需要连接器（connector）授权的工具"这条捷径在
这次会话的授权范围内不成立。警告信息本身给了两个方向：从"持有连接器的
会话"里建（这次会话显然不满足，即使绑定的是自己），或者去 claude.ai
的 Routines 界面手动建、在那里把 GitHub 连接器接上——后者需要仓库
所有者本人操作，这次会话做不到。

**当前实际能用的守夜手段，只剩下已经在跑的那条**：`send_later`
（trig_01J2EG5uR8DQPuwAUxzD7CvJ，明天约 UTC 14:35 触发）——它只是发一条
提醒消息把这个会话唤醒，不需要连接器，唤醒之后本会话原本就有的
`mcp__github__` 工具照常可用，跟今天检查 schedule 记录用的是同一套。
明天的判断依据没有变，只是"多一条独立备份路径"这个设想落空了。
