# 2026-09-06　关闭自动发布：校验过也不直接上线，改成人工逐篇选发

## 背景

仓库所有者提出要求：不想再让流水线校验一过就自动上线，以后自己在
`posts/` 里挑要发的文章、手动放行。

翻代码发现这条口径本来就有一半基础设施——`draft: true` 这套「放行 = 删
一行」的机制早在 [2026-08-26　草稿位放行](2026-08-26-草稿位放行.md) 就
做好了，`seed.process()` / `manual.py` 也早有 `publish` 参数控制
`live = ok and publish`。**缺的只是 `.github/workflows/publish.yml` 里
那一行默认值**：

```yaml
PUBLISH: ${{ github.event.inputs.publish == 'false' && '' || '--publish' }}
```

`inputs.publish` 在定时触发（`schedule`）和 `drafts/**` 推送触发
（`push`）时都不存在（不是字符串 `'false'`），落到 `||` 右边，等价于
「默认直接发布」。也就是说，每晚 21:13/23:37 的定时任务、以及往
`drafts/` 推稿子，校验一过就直接跳过草稿位上线，人完全插不上手——这正是
「放行机制」和「默认行为」两层脱节的地方：放行机制是安全阀，但默认值
从没经过这道阀。

排查时顺带翻出 `run_auto()`（`mode: auto`，旧的多篇重组通道）压根不认
`--publish` 这个开关：它的 `draft=not res.ok` 完全没有 `publish` 参数
参与判断，只要校验过就无条件直接发布，跟 `seed.process()` 的
`live = ok and publish` 口径不一致。这个通道现在只能靠手动
`workflow_dispatch` 选 `mode: auto` 触发，但真选中它的话，即便这次改动
把 `publish` 开关默认关掉，`auto` 通道照样绕过去直接发——「不勾 publish
就不自动发」这条线在它身上是假的，顺手一起补上。

## 变更

- 修改：`.github/workflows/publish.yml` 的 `publish` 开关默认值
  `true` → `false`；`PUBLISH` 环境变量的判断逻辑从「不显式传 `false`
  就发布」反过来改成「显式传 `true` 才发布」——定时、`drafts/**` 推送
  两种触发方式都拿不到 `inputs.publish`，改完之后统一落空字符串，一律
  走草稿位
- 修改：`pipeline/main.py` 的 `run_auto()` 新增 `publish=False` 参数，
  改用 `live = res.ok and publish` 决定是否落草稿位（原来是
  `draft=not res.ok`，完全不看 publish 开关），跟 `seed.process()` 的
  口径对齐；CLI 侧 `main()` 把 `a.publish` 传进去
- 修改：`README.md` 里描述「发布节奏」「架构总览」「手动触发一次发布」
  「人工投稿」四处的措辞，去掉「校验过就自动/直接发布」的旧说法，改成
  「默认落草稿位，需要手动触发且显式勾选 `publish` 才直接发布」
- 新增：自检 `test_run_auto_default_is_draft_even_when_verification_passes`
  ——不依赖真实 vault，专门钉死「`run_auto()` 不传 `publish` 时，哪怕
  校验全过也必须落 `draft: true`」这条安全阀

## 实现

**改的是默认值，不是新功能。** 草稿位机制、`publish` 参数、放行流程
（删 `draft: true` 那一行）都是现成的，本次只是把「谁走这条草稿位」的
默认判断从「几乎不会」改成「几乎总会」。选择只动 `PUBLISH` 环境变量的
判断表达式，而不是拆分成三条触发方式各自配置，是因为改完之后语义统一
成一句话：**只有手动触发且显式勾 `publish` 才直接发布**，不需要在
`schedule` / `push` / `workflow_dispatch` 三处分别维护「这条触发方式该
不该自动发」的规则，少一处以后忘记同步的地方。

**`run_auto()` 补 `publish` 参数而不是弃用这条通道。** 校验通过与
`publish` 开关是否直接发布，这是流水线三条 AI 通道（`seed` / `manual`
/ `auto`）该共有的口径，`auto` 通道少这一半逻辑是历史遗留（这条通道本身
README 里也标注"已不作为默认"），但既然还留着手动触发的入口，就该跟其余
两条通道守同一条规矩，不然「不勾 publish 就不自动发」这句话对这一条通道
是假的。

**没有改校验规则本身。** 这次改动全程没有碰 `pipeline/verify.py`——
「校验过不过」和「过了要不要直接发布」是两件事，安全阀本身没有放宽，只是
上面多加了一道人工确认。

## 验证

**自检 163/163 全绿**（含新增的 1 项），`npm run build` 通过，49 个
页面正常生成，无报错。

**手动推演三条触发路径，确认都落草稿位：**

- 定时触发（`schedule`）：`github.event.inputs.publish` 不存在，
  `== 'true'` 为假 → `PUBLISH` 为空字符串 → 不传 `--publish` → 无论
  `seed`/`manual` 哪条通道，校验过了也落 `draft: true`
- `drafts/**` 推送（`push`）：同上，`inputs.publish` 不存在，同样落空
- 手动触发（`workflow_dispatch`）：不勾 `publish`（新默认）同上；显式
  勾选时 `inputs.publish == 'true'`，`PUBLISH` 才变成 `--publish`，这时
  校验过了才会跳过草稿位——这是唯一还能直接发布的路径，且需要人在
  Run workflow 界面主动勾选

**没有改动放行路径本身**：仍然是「去 `posts/` 对应月份的文件里删掉
`draft: true` 那一行，提交」，验证方式沿用
[草稿位放行](2026-08-26-草稿位放行.md) 里实测过的那一套，本次未重复
验证（未改代码路径）。
