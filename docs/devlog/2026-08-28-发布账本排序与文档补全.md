# 2026-08-28　发布账本按时间倒排，补 published.json 字段说明与手机端手动发布文档

## 背景

用户改用手机 GitHub App 手动触发 `publish` workflow（见对话记录：先确认了
`workflow_dispatch` 比 `schedule` 可靠，再在手机上实际点了「运行工作流」）
之后，想直接在手机上打开 `published.json` 确认这次到底有没有真的发布成
功——发现这个文件是 dict 插入顺序，最早发布的排最前，手机小屏幕要一路拉
到文件末尾才能看到最新一条，很不方便。

顺着这个问题追问出另外两处文档缺口：README 里提到 `published.json` 的地方
都是三言两语（「发布状态账本」「按 slug 记录」），没有一处逐字段说明每个
键的含义；「手动触发一次发布」那节只写了网页版 Actions 的操作路径，没提
手机 GitHub App 怎么点、有什么已知的平台差异。

## 实现

**排序只收口在 `save_published()` 一处，不去改每个写入点。** 写
`published.json` 的路径不止一处：`record_published()`（引子通道、auto
通道都走它）、`reconcile()` 里的账本迁移和补建逻辑（会直接 `del`/重新赋值
key）。如果在每个写入点分别做「插到最前面」，容易漏掉一处，`reconcile()`
内部的增删还会把手动维护的顺序假设弄乱。改成只在落盘前统一重排，不管内存
里那份 dict 当下是什么顺序、被谁怎么改过，写到磁盘上的结果永远正确——
改动面是一个函数，不是好几处。

**排序算法：先整体反转，再按 `published_at` 做稳定排序（`reverse=True`）。**
如果直接 `sorted(items, key=日期, reverse=True)`，同一天发布多篇时，
Python 的稳定排序会保留这些元素在排序前的相对顺序，也就是「先写的仍排
前面」——跟「最新的在最上面」的直觉不一致（同一天里应该是后写的更接近
「最新」）。先把列表整体反转一次再排序，稳定排序保留的就是「反转后的顺序」，
等价于「同一天内，写入更晚的排更前」。这是这次实现里最不直观的一行，代码
注释里写清楚了推导过程，不指望看一眼就懂。

**存量的 16 条记录一次性重排，不是只对以后新写入的生效。** 跑了一次
`load → save_published`（不经过 `reconcile`，避免触发对账逻辑改动字段
内容）在本地把现有文件重排了一遍，随这次改动一起提交。这样用户合并后
立刻能看到效果，不用等下一次发布才验证。重排前后做过逐字段比对：
key 集合相同、每条记录的字段值完全相同，纯粹是顺序变化，没有数据丢失
或篡改。

**没有改 `published.json` 的数据结构本身。** 考虑过用数组包一层、或者
加一个显式的序号字段，但现有的「dict by slug」结构本身承担着核心的去重
判断职责（`in published`、`published[slug]` 遍布 `seed.py`/`select_.py`/
`drafts.py`），改结构要动全部读写点，风险和这次「让文件好读」的诉求完全
不成比例。排查过所有 `published.values()`/`.items()` 的用法，全部是构造
查找表或去重集合，没有一处依赖顺序，改落盘顺序不影响任何现有判定逻辑。

**站点构建不读这个文件，重排不影响前端。** `src/lib/posts.ts` 里出现过
「published.json」这几个字，但只是注释文字，实际代码只读
`getCollection('posts')`（Astro content collection，来自文章 frontmatter），
`published.json` 纯粹是 pipeline 自己的记账本，不是站点运行时的数据源。

**两处 README 补充都接在已有小节后面，没有新开二级标题。** 字段说明是
「账本自己会对账，不用手动维护」这节的自然延伸（同一个文件的两个侧面：
它怎么维护自己 vs. 它每个字段是什么意思），手机端操作是「手动触发一次
发布」这节本来就该覆盖的内容，只是之前漏了移动端。目录只列到二级标题，
两处都不用同步改目录。

## 验证

- **`python pipeline/test_pipeline.py`：138/138 全绿**（137 → 138）。新增
  的自检构造了「旧/中-先/中-后/新/没日期」五条记录验证：不同日期严格
  降序、同一天内后写入的排更前、`published_at` 缺失时不报错且排最后
- **存量数据重排前后逐字段比对**：脚本核对 `set(old) == set(new)` 与
  `all(old[k] == new[k] for k in old)` 均为 `True`，确认只是顺序变化，
  没有引入数据改动
- **`npm run build`：29 个页面构建成功**，确认 `published.json` 排序
  变化不影响 Astro 构建产物（前端本来就不读这个文件）
