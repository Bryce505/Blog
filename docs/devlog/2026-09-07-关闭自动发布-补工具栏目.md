# 2026-09-07　关闭自动发布：补上工具与效率栏目漏掉的草稿位

## 背景

[2026-09-06　关闭自动发布](2026-09-06-关闭自动发布.md) 合并上线后，
仓库所有者当晚（2026-09-06）就发现问题没解决：定时任务 21:13 和 23:37
两次都跑了，`src/content/posts/2026-09/` 下还是多出了 `tools-readme.md`、
`tools-chapter5_enzymes-...md`、`tools-重组乌司他丁-cde审评意见答复-药学
部分.md` 三篇没人要的文章，全部无 `draft` 字段、直接上线，事后手工删了
三个文件（`4043deb`、`51e0fcc`、`fa29161`）。

排查发现：前一天的改动只堵住了 `seed` / `manual` / `auto` 三条 AI 通道
（都走 `PUBLISH` 环境变量 → `--publish` 参数 → `live = ok and publish`
这条链路），漏了 `run()` 里最先跑的那一步——「工具与效率栏目」：

```yaml
- name: 工具与效率栏目
  run: python pipeline/main.py --routinerun .routinerun --blog . | tee -a report.json
```

这一步不带 `$PUBLISH`，`routinerun.run()` 也压根没有 `publish` 参数，
`_all_posts()` 里查不到就直接落盘、无条件 `status: 'published'`。三篇
误发的文章都是这条通道产出——`tools-` 前缀就是它的 slug 规则
（`'tools-' + slugify_cn(...)`）。它跟 AI 通道不一样，不经过
`verify.py`，但「校验用不上」不等于「不需要人工确认要不要上线」：
RoutineRun 私库里随手记的工作笔记（含占位 README、内部审评材料），只要
正文过了 `MIN_BODY_CHARS`（500 字符）这道占位过滤，就会被当成「够格发布
的笔记」——这道过滤本来是用来剔除占位 README 的，不是用来判断「这篇该
不该公开」的，两者被默认捏在了一起。

**根因**：昨天的改动默认三条 AI 通道以外没有别的地方在往 `posts/` 写
文章，实际上流水线一次运行有五条通道会写文章（[README「五条通道」](../../README.md#五条通道)），逐条核对时漏了这条不经过校验器、因此
容易被忽略的通道。

## 变更

- 修改：`pipeline/routinerun.py` 的 `run()` 新增 `publish=False` 参数，
  不传时 frontmatter 最前面加 `draft: true`，`status` 相应改成
  `'draft'`；已存在则跳过的判重逻辑不变
- 修改：`pipeline/main.py` 的 `--routinerun` CLI 分支透传 `a.publish`；
  模块顶部通道说明补上这条通道
- 修改：`.github/workflows/publish.yml` 的「工具与效率栏目」步骤加上
  `$PUBLISH`，跟「发文」步骤共用同一个开关
- 修改：`README.md`「五条通道」表格里工具与效率那一行，补上「同样默认
  落草稿位」
- 新增：自检 `test_routinerun_default_is_draft`——不传 `publish` 时，
  哪怕笔记体量正常也必须落 `draft: true`

## 实现

**复用同一个 `$PUBLISH` 开关，不单独给这条通道加一个开关。** 用户的
诉求是「以后我手动选择要发的文章」，这该是流水线全局的默认姿态，不是
按通道各自配置——单独开一个开关只会在下次新增通道时再漏一次。

**判重逻辑不变，不追溯处理旧文章。** 已经上线的 `tools-*` 文章（不带
`draft` 字段）跟这次改动前发布的其他文章一样，只在下次源笔记变化被
重新选中时才会被这条通道的存在性判重挡住，这次改动不会把它们收回草稿
——「放行 = 删一行，退稿 = 删文件」这条规矩里没有第三种状态。

**为什么当时会漏掉。** 复盘时定位到根因是「三条 AI 通道」这个心智模型
本身不完整：`run_auto()` / `seed.process()` / `manual.run()` 共享
`verify.py` 的校验框架，容易被当成「AI 生成内容」的全部；但 README 早就
把 `routinerun` 单列成第五条通道（不经过 AI、不经过校验），审这类改动时
应该按「往 `posts/` 写文件的地方」逐处核对，而不是按「用到 AI 的地方」
核对——校验器和发布开关是两件独立的事，昨天的改动混淆了这一点。

## 验证

**自检 164/164 全绿**（含新增的 1 项），`npm run build` 通过，49 个
页面正常生成，无报错。

**手动核对了这次会不会重复出现同样的漏判**：流水线一次运行会往
`posts/` 写文章的一共五处入口——`run_auto()`、`seed.process()`、
`manual.run()`（经 `drafts.fill_defaults` 走 `--manual`）、
`drafts.run_drafts()`（`--drafts`，人已手写好、决定要发，故意保持
无条件发布，不是漏判）、`routinerun.run()`。前三处 2026-09-06 已经
接了 `publish` 开关，这次补上第五处；`run_drafts()` 是唯一保持原样
的，README 里「人工投稿」一节已经写清楚它跟 `--manual` 的区别。
